# Behavioral comparison — 2026-11-07

## Procedure and evidence

Baseline: repository commit `dfe8d6468571eb3636c9cf2d049aeb6ca4867213`. Candidate: the accompanying skill revision. The skill's name, invocation policy, and language preference rules were preserved.

Two independent responding agents received isolated copies of the relevant skill and requests containing only case IDs and user prompts. They received no plan history, suspected defects, expected answers, or acceptance criteria. Both used the same inherited model configuration. Each was instructed to treat every request as a new conversation and to produce actual user-facing answers, including questions when needed. No user replies were simulated, and no external applications were accessed.

The baseline agent answered the nine comparison cases. The candidate agent answered the same nine plus two supplemental founder cases. Both could read the supplied skill's relevant references. The baseline read the entrypoint and founder guidance; the candidate also read decision calibration. Neither read provenance. The primary implementer then read the actual answers and assessed them against [the behavior-level criteria](cases.json).

Raw responses are retained in [baseline.md](responses/baseline.md) and [candidate.md](responses/candidate.md). These are generated answers to fictional requests, not personal advice or real user data. They are evaluation artifacts outside the installable skill.

## Limits

This was one response per case per version, with two separate agents processing batches under fresh-conversation instructions rather than a separate model process for every case. No multi-turn outcomes, long-term user decisions, trigger-selection benchmark, or repeated stochastic runs were tested. The implementer assessed the responses manually after generation; the assessment was not independently blinded.

The cases exercise the requested changes and selected regressions, not all possible life, research, creative, or founder decisions. Passing them does not establish a universal strategy method or guarantee reliable behavior across clients and models. Re-run affected cases when a real usage failure or a material instruction change warrants it.
